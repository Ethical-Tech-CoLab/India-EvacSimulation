## Documentation drift

- **`Evacuation_Simulator_Methodology.docx` is v1.0 and already behind the code.** It documents `MC_RUNS = 100`; the code runs 500. It lists "Counterfactual MC" for information value as a §13 *future extension*; `computeInfoValue`/`assignForInfoValue` already implement exactly that. It doesn't mention the greedy urgency-ordered assignment with capacity contention (§7 in-app methodology), describing independent assignment instead. It predates the Willingness → gatekeeper change made in this session. Recommend bumping it to v1.1 with a short changelog section, or adding a `CHANGELOG.md` that the docx references rather than trying to keep prose in sync with code on every change.
- **The docx claims to be "auto-generated from the simulator source code structure"** (closing line). It isn't — it's manually authored prose that happens to track the code. Either build a real generation step (even a script that extracts `PARAMS`/`PARAM_DOCS` into a table) or soften the claim, since an examiner who checks will find hand-written text, not generated output.
- **`explainer.html` had drifted from `index.html` in at least three places before this session** (MC run count, "two gatekeepers" vs the code's structure, and an assignment-independence claim that was no longer true). It's now corrected and cross-linked via `#card-N` anchors, but nothing prevents it from drifting again on the next feature change. Since it's a second prose description of the same model as the in-app Methodology accordion, consider whether it should exist as *generated* HTML from a shared source (e.g. a JSON/YAML description of factors, controls, and cards) rather than hand-maintained twice.

## Modelling

- **Sensitivity chart (`buildCurves`) can select a capacity-infeasible destination, producing a non-monotonic or falsely-zero curve.** Discovered while producing ERUS-Paper.md §6.10. `buildCurves` picks the "best" destination at each uncertainty level using `compositeScore` alone (engine.js), which only *discounts* insufficient capacity via `capFit`, whereas the actual assignment step `assign` *excludes* capacity-infeasible destinations from consideration entirely. For seed 42/N=8/M=3, the 632-person "Unaccompanied minors" group's curve is verified to be flat at 0% success from 0–40% uncertainty (because the highest-composite destination in that range, Station Hotel, holds only 545 people, so every Monte Carlo trial fails the `dest.capacity >= group.size` check regardless of readiness) and then jumps to 22.4% at 50% uncertainty when a different, capacity-sufficient destination becomes the top composite score. The rise looks like uncertainty *helping* that group, which contradicts the chart's own stated purpose. Proposed fix: filter `buildCurves`' per-level destination candidates by `d.capacity >= group.size` before ranking by composite score, matching `assign`'s viability filter — a small, contained change now that the logic lives in `engine.js` and is covered by `tests/engine.test.js`. Not applied in this pass because it changes displayed results in a live, publicly-linked tool that may already be cited elsewhere; needs the author's sign-off first, and the worked-example numbers in ERUS-Paper.md §6.10 would need re-running against the fixed version afterward.

- **Factor Information Value panel's ranking is not resolvable from sampling noise at its default 100 runs.** Discovered while producing ERUS-Paper.md §6.11. Run against seed 42/N=8/M=3 at 30% uncertainty, three of seven factors show a *negative* estimated gain from resolving their Unknown instances to Operational (Willingness −6.7pp, Security −6.0pp, Food & water −4.3pp), which is impossible in the underlying model — an Operational status can only raise or hold a factor's score, never lower it (§5.2, §5.4). At a ~30% baseline success rate and 100 runs, the estimator's standard error is roughly 5–6 percentage points per side, comparable to every reported delta except possibly Willingness. `PARAM_DOCS.MC_RUNS`'s sibling constant `INFO_RUNS` (currently hardcoded to 100 inside `computeInfoValue`, not in `PARAMS`) is the natural fix target: either raise it, average across repeated seed offsets, or surface the standard error alongside each delta so a reader doesn't read noise as signal. Not applied in this pass — same reasoning as the item above, plus this one is a UI/reporting decision (how much run-time cost is acceptable) as much as a code fix.

- **Willingness's promotion to gatekeeper status is a substantive behavior change, not just a label fix.** In a default-seed run (seed 42, N=8, M=3) it took the excluded-destination count from roughly 2/8 to 5/8, because gatekeeper factors are generated with a 24% blocked-probability weight vs. 10% for standard factors. That's the intended fix (an unwilling host should exclude a site), but it changes the "shape" of every scenario materially. **The seed-42 exclusion rate is now pinned exactly** — 5 of 8, not just "roughly" — by `tests/engine.test.js`, so it can no longer drift silently, but the broader multi-seed sweep this item originally asked for (re-running across many seeds to confirm 5/8 is typical rather than seed-42-specific) is still undone. Before citing results from this version in the thesis, run that wider sweep / sensitivity analysis the methodology doc already recommends in §11, specifically on `GATEKEEPER_WEIGHT` and the gatekeeper status-distribution array (`[.30,.28,.24,.18]`), to confirm the new exclusion rate is intentional and not an artifact of reusing the security/authority distribution for a conceptually different factor.
- **§13 of the methodology doc lists five other future extensions** (factor correlation, temporal dynamics, real data integration, a counterfactual "what if" UI) that remain undone. Of these, **factor correlation** (security and consent plausibly co-vary in real conflict) is probably the highest-value next step for ecological validity, since it's flagged as a known limitation in both the doc and the in-app §7 Assumptions section.
- **The 40% success threshold and the ±1 ordinal perturbation are both acknowledged-uncalibrated assumptions.** If empirical UNHCR/IOM displacement data (the "Real data integration" extension) ever gets pulled in, these are the two parameters most worth checking against it first.
