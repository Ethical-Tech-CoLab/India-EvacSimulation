## Modelling

- **Sensitivity chart (`buildCurves`) could select a capacity-infeasible destination, producing a non-monotonic or falsely-zero curve.** Discovered while producing ERUS-Paper.md §6.10. `buildCurves` picked the "best" destination at each uncertainty level using `compositeScore` alone, which only *discounts* insufficient capacity via `capFit`, whereas the actual assignment step `assign` *excludes* capacity-infeasible destinations from consideration entirely. For seed 42/N=8/M=3, the 632-person "Unaccompanied minors" group's curve was flat at 0% success from 0–40% uncertainty (because the highest-composite destination in that range, Station Hotel, holds only 545 people, so every Monte Carlo trial failed the `dest.capacity >= group.size` check regardless of readiness) and then jumped to 22.4% at 50% uncertainty when a different, capacity-sufficient destination became the top composite score. **Fixed.** `buildCurves` now filters candidates to `d.capacity >= group.size` before ranking by composite score, matching `assign`'s viability filter, falling back to the unfiltered set only if no destination has enough capacity for the group at all. Verified via headless Chrome that the primary-assignment numbers in §6.8/§6.9 (which depend on `assign`, not `buildCurves`) are unchanged, and `tests/engine.test.js` still passes 22/22. ERUS-Paper.md §6.10 has been re-run against the fix and rewritten.

- **Factor Information Value panel's ranking was not resolvable from sampling noise at its original default of 100 runs.** Discovered while producing ERUS-Paper.md §6.11. Run against seed 42/N=8/M=3 at 30% uncertainty, three of seven factors showed a *negative* estimated gain from resolving their Unknown instances to Operational (Willingness −6.7pp, Security −6.0pp, Food & water −4.3pp), which is impossible in the underlying model — an Operational status can only raise or hold a factor's score, never lower it (§5.2, §5.4). At a ~30% baseline success rate and 100 runs, the estimator's standard error was roughly 5–6 percentage points per side, comparable to every reported delta. **Fixed.** The run count is now `PARAMS.INFO_RUNS`, raised from a hardcoded 100 to 500 (matching the main Monte Carlo engine's `MC_RUNS`), which cut every delta in the seed-42/N=8/M=3 scenario to within about a percentage point of zero. ERUS-Paper.md §6.11 has been re-run and rewritten with the corrected numbers.

- **Willingness's promotion to gatekeeper status is a substantive behavior change, not just a label fix.** In a default-seed run (seed 42, N=8, M=3) it took the excluded-destination count from roughly 2/8 to 5/8, because gatekeeper factors are generated with a 24% blocked-probability weight vs. 10% for standard factors. That's the intended fix (an unwilling host should exclude a site), but it changes the "shape" of every scenario materially. **Fixed / resolved.** The seed-42 exclusion rate is pinned exactly at 5/8 by `tests/engine.test.js`, and the multi-seed sweep this item asked for has now been run: across 500 seeds at N=8, the mean exclusion count is 4.48/8 (56%), with 4 and 5 the two most common outcomes (just over half of all seeds), and seed 42's 5 sits inside that main mass, not at an extreme. This matches the theoretical rate the peer review independently derived from the code, P(at least one of three gatekeepers blocked) ≈ 0.56, confirming the roughly-five-in-eight rate is the model's typical, intended behaviour at these parameters rather than a seed-42 artefact. Recorded in ERUS-Paper.md §7.3. Whether 56% is empirically *correct* for a real evacuation context remains a separate, genuinely open calibration question (no real field data exists to check it against) — that part of this item cannot be closed without data this project doesn't have.
- **§13 of the methodology doc lists five other future extensions** (factor correlation, temporal dynamics, real data integration, a counterfactual "what if" UI) that remain undone. Of these, **factor correlation** (security and consent plausibly co-vary in real conflict) is probably the highest-value next step for ecological validity, since it's flagged as a known limitation in both the doc and the in-app §7 Assumptions section.
- **The 40% success threshold and the ±1 ordinal perturbation are both acknowledged-uncalibrated assumptions.** If empirical UNHCR/IOM displacement data (the "Real data integration" extension) ever gets pulled in, these are the two parameters most worth checking against it first.
- **Mobility-need blind spot in `vulnerability_match` (`compositeScore`, engine.js).** A group whose stated need is `mobility` is scored against the same check as a `medical` need — whether the destination's Medical capacity factor is Operational — so mobility needs have no independent representation anywhere in the model (ERUS-Paper.md §5.8, §12.7; peer review m7). Proposed fix, not yet implemented: add an eighth destination factor (e.g. `accessibility`), generated and scored the same way as the existing seven, and check `group.needs === 'mobility'` against it in `compositeScore` the way `medical` is checked today. Not done in this pass because it changes the gatekeeper/standard weight balance and the shape of every generated destination — a modelling decision, not a mechanical fix, and one that would also require re-running every worked example in ERUS-Paper.md §6.
